# 05 — What to do with each CI and release piece: keep, replace, simplify or drop (question E)

Written on Wednesday 30 September 2026. Research only: no repository was changed.

## Terms used in this file

- **Piece.** One part of harness-kit's or the gadget's CI and release process: a script, a workflow job, a configuration file, or a hook. A row below describes one piece.
- **KEEP** means leave it as it is. **REPLACE** means use another component instead, and the row names it. **SIMPLIFY** means keep the job but make it smaller, faster or less custom. **DROP** means stop doing it, and the row names what stands in for it. These four words are my judgement, so every verdict is an [ASSUMPTION] built on the evidence in files 01 to 04.
- **Gate.** A check that can stop a bad change from reaching `main` or a release. **Gate strength after the change** says whether the gate is the same, stronger, or (for a few rows) only equal once a named condition holds.
- **Targeted replay and full replay.** As defined in file 02: the targeted replay runs only the faults tied to the changed files, the full replay runs all 137.
- **Machinery.** The 7 files listed in `.harness/replay-machinery`, whose change makes CI run a full replay on a branch push.
- **Baseline part, shard, verdicts job.** The three stages of the current replay in CI: one whole-check run that measures time, 8 parallel slices of the faults, and one job that judges all results together.
- **Aggregator (gate) job.** One last job that succeeds only when all real jobs succeeded, so branch protection names one check. **Ruleset, required check, fast-forward, concurrency group.** As defined in file 01.
- **Gadget.** The control-chart-gadget repository. **Consumer project.** A repository that installs harness-kit; the gadget is the only one.

## CONTRADICTIONS

1. **There is one version file, not two.** My own earlier working note said harness-kit's version lives in two files. That was wrong. [VERIFIED | clone at e275280 and Claude Code's plugin documentation] The version is in `plugins/harness-kit/.claude-plugin/plugin.json` only. The marketplace file deliberately carries none, and `tests/validate.sh` forbids one. It is bumped inside each work commit, not at release time. So any design that needs "bump the version at release" is not what your repository does today.
2. **The run on `main` is the first replay for a normal change, and a duplicate only for machinery changes.** [VERIFIED | `validate.yml` lines 100–160] The replay jobs run on a push to `main`, on the weekly schedule, on a manual start, and on a branch push only when `machinery` is true. Removing the run on `main` is therefore not a "remove a duplicate" change: it removes the only replay a normal change gets today, so it must wait until the replacement (a targeted replay on the branch, a full replay at release) exists and has been proved. This is why every DROP below names what stands in for it.
3. **A tag push starts the `validate` job too.** [VERIFIED | `validate.yml`: `on: push:` has no filter, so it fires for tags as well as branches] So a release costs one more `validate` run than the description suggests (the tag run), and the tree it tests is the one the branch already tested. [ASSUMPTION for the tree equality, from "the tag is made at the branch head"]
4. **`validate` runs the review check, and a replay run does too.** `validate.yml` runs `bash tests/validate.sh` without `--skip-reviewed`, while `.harness/check-command` says `bash tests/validate.sh --skip-reviewed`. [VERIFIED | both files] `check-reviewed.mjs` is documented as a CI check that the branch's current diff was reviewed and the verdict was PASS. So CI, not your Mac, is what enforces "no unreviewed diff", and it enforces it on the branch run. Any redesign that stops running `validate` on some pushes must keep that check running on the branch that carries the diff. On `main` after a fast-forward the diff to `origin/main` is empty, and an empty diff passes, so the run on `main` adds nothing for that check. [PARTIAL | header of `check-reviewed.mjs`: "An empty diff hashes to `none`" and "PASS when ... the diff is empty"]
5. **Seven faults each run a whole check, not one test file.** [VERIFIED | my count; mechanism in `tests/validate.sh` lines 44–60] This is a cost that no file in your description mentions (file 02, contradiction 4).
6. **Your belief "custom scripts are safer than pull requests" is partly right at the hook layer.** [VERIFIED | Anthropic's permissions page; file 04, contradiction 3] `git-guard.mjs` handles command forms that a native deny rule does not, so it is KEEP below. The belief is unsupported for the merge and release steps (file 01, contradiction 4).

7. **Neither `ship.sh` nor `release.sh` runs a fault replay, and harness-kit's own header tells consumer projects not to run it in CI.** [VERIFIED | search of the whole plugin folder for `replay-faults`: the only callers are `land.sh`, the CI workflow and reports] `replay-faults.sh` says: "LOCAL ONLY ... Do not add it to a consumer project's CI: a private repository pays for its Actions minutes." So for the gadget an ordinary change made through `ship.sh` is replayed only if you run `replay-faults.sh` by hand, or a protected-file patch goes through `land.sh` (which runs the tied faults). Whether the gadget's `scripts/check.sh` or a hook runs it: NOT FOUND. For harness-kit itself, `validate.yml` says in a comment: "a fault any other merged change let SURVIVE shows up here, after the merge, as a red run on main." That is your own description of the late surprise.
8. **`release.sh` and `ship.sh` push the branch themselves, so for most changes the branch push and the release happen at the same moment.** [VERIFIED | `release.sh` header, step 3: "Push the branch to origin"] Whether you ever push a branch by hand earlier: NOT FOUND. This matters for the design: a replay "on every branch push" is, for most changes, a replay at release time, so its value over a full replay before the merge is speed, not earlier warning.

## Strongest counter-cases

- **Against dropping the full replay on `main` (rows 1.8, 1.1).** Two failures are plausible. The hand-written map in `check-files` may miss a dependency, so a targeted replay skips a fault that a change breaks; and the run on `main` is also an independent check on a clean runner with the current image and installer, which can change between the branch run and the `main` run. The full replay at release, the weekly full run and the machinery rule cover most of both, not all. If quality must not drop at all and step-0 measurements show a full replay on every branch push is fast enough, full-on-branch is the simpler and stronger option, and none of the DROP rows should be done.
