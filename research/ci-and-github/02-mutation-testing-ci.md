# 02 — Mutation testing in CI, and how harness-kit's fault replay compares (question B)

Written on Wednesday 30 September 2026. Research only: no repository was changed.

## Terms used in this file

- **Mutation testing.** A tool makes one small change to a program (for example it turns `<` into `<=`). This changed copy is called a **mutant**. The tool then runs the tests. If some test fails, the mutant is **killed**, which is good. If every test still passes, the mutant **survived**, which means the tests have a gap.
- **Mutation score.** Killed mutants divided by all mutants, as a percentage. Infection (a PHP tool) calls it MSI, "mutation score indicator".
- **Fault replay (harness-kit's word).** A fixed, hand-written list of breaks. Each entry in `.harness/mutations.tsv` (137 entries) says: in this file, replace this exact text with that text, and then this one named check must fail. The tool plants the break in a throwaway copy of the code and confirms that the check fails. In this file I call each entry a **fault**.
- **Targeted replay.** A replay that runs only the faults tied to files changed since the base branch. A **full replay** runs all 137. `replay-faults.sh --plan` prints which one it would run.
- **Diff-scoped run.** A mutation run that mutates only the lines or files changed between a branch and its base.
- **Incremental run.** A run that reuses stored results from an earlier run for everything that has not changed.
- **Shard.** One of several machines that each run a slice of the work at the same time.
- **Baseline.** A first run of the unchanged code, to confirm that the tests pass and to measure how long they take. Timeouts for mutants are derived from it.
- **Post-merge run.** A run that starts after a change has landed on `main`. A **pre-merge run** happens before it lands.
- **Fast-forward.** Moving `main` to a commit that already contains all of `main`, so the commit that lands is exactly the commit that was tested.

## CONTRADICTIONS

These are places where the evidence disagrees with what the brief says you believe, or where I found something the brief did not say.

1. **"A full fault replay on every push to `main` is necessary" is not how the sampled projects work.** [PARTIAL: sample not random] Of the nine, 5 do run a full-scope mutation run after a push or merge (stryker-js, Infection, mutation-testing-elements, checkstyle, and cargo-mutants on every relevant push), so a post-merge full run is not unusual. But the other four do not: PHP-CS-Fixer and phpstan-src run mutation testing **only on pull requests**, and Stryker.NET runs its full run only nightly. (A ninth, phpstan-doctrine, has a job that is configured to run on pull requests and on pushes, but its command reads `$GITHUB_BASE_REF`, which I expect is empty on a push, so in practice it is a pull-request job. [ASSUMPTION: I did not fetch GitHub's documentation for that variable].) So the accurate statement is: "not required in every mature project", and it is not "proved unnecessary for harness-kit".
2. **"Faults must be replayed after the merge, on `main`" is the opposite of the mainstream shape.** [VERIFIED for the workflow files of PHP-CS-Fixer and phpstan-src] The mainstream shape is to catch a surviving mutant before the merge, on the changed lines. PHP-CS-Fixer's own workflow says: "we run mutations tests only for diff between branches". Where a post-merge or nightly full run exists, it is the slow safety net behind the pre-merge scoped run, not the first place a surviving mutant is found.
3. **harness-kit already owns the mainstream building block and does not use it in CI for ordinary changes.** [VERIFIED | `plugins/harness-kit/scripts/replay-faults.sh` header and `.github/workflows/validate.yml`, commit e275280] A plain run of `replay-faults.sh` is already a targeted replay: it picks only the faults tied to files changed since the merge base with `main`. But `validate.yml` runs faults in CI only for pushes to `main`, the weekly schedule, a manual start, and a branch push that changes one of the 7 machinery files. So for a normal change, the first replay in CI happens on `main`. That is exactly the "late surprise" you described, and it explains how `main` went red after releases four times in two days. The equivalent of cargo-mutants' `pr-mutants` job and Infection's `--git-diff-lines` job exists as code in your repository and is simply not wired into ordinary branch runs.
4. **New finding: 7 of the 137 faults cannot be run against one test file, so each of them runs a whole check.** [VERIFIED | my count from `.harness/mutations.tsv` and `.harness/check-files`; the mechanism is in `tests/validate.sh` lines 44–60, which print "lists no test file for …, so the whole check runs"] The seven are `defects-broken-line`, `ci-replay-shard-dropped`, `ci-shards-not-needing-baseline`, `ci-baseline-timeout-under-fallback`, `ci-session-at-job-timeout`, `stop-gate-limit-over-hook` and `plan-no-verification-section`. Every other fault runs only its own test file. If a whole check costs roughly what one CI run of `tests/validate.sh` costs (2m13s to 2m40s for the whole job on 29–30 September), those seven cost about 15 to 19 machine-minutes in every full replay. [ASSUMPTION: derived from your run times, not measured per fault] Whether that is a large share of the full replay is NOT FOUND, because the per-fault time of the other 130 faults is not in any file I read.
5. **The hand-written map from check name to test file is where quality could silently drop.** [VERIFIED for the mechanism; ASSUMPTION that a gap exists] Every mature tool that narrows a run by change either measures coverage automatically (Pitest, Stryker `perTest`, Google's line coverage) or states the limit of its narrowing in its own documentation (section 3). harness-kit's targeted replay depends on `.harness/check-files` (308 lines, written by hand). If a fault's real dependency is missing from that map, a targeted replay could skip a fault that a change breaks, and nothing would tell you. I did not test whether such a gap exists.

## 1. Does mature practice have a name for harness-kit's approach?

**Result: no exact name was found.** Three near matches exist, and each differs in an important way.

1. **Tailored mutation operators** (Allamanis, Barr, Just and Sutton, "Tailored Mutants Fit Bugs Better", 2016). [PARTIAL | extract of the authors' technical report | 2026-09-30] "Tailored mutation operators are built from and apply to an existing code base and its version history. They can, for instance, identify and replay errors specific to the project for which they are tailored." This is the closest idea: put back a break that history has proved. The difference is that their operators are patterns mined from history and applied across the code base to generate many mutants, whereas harness-kit replays each historical break as one exact text substitution.
2. **Hand-seeded faults.** [PARTIAL | extract of Andrews, Briand and Labiche, ICSE 2005] "These faults can be introduced by hand (the experimenter can for instance ask experienced engineers to do that)." That literature uses seeded faults to compare test techniques in experiments; it does not describe a standing gate that runs on every change.
3. **Meta's ACH** ("Mutation-Guided LLM-based Test Generation at Meta", arXiv 2501.12862, 22 January 2025). [PARTIAL | extract] "ACH generates relatively few mutants (aka simulated faults), compared to traditional mutation testing. Instead, it focuses on generating currently undetected faults that are specific to an issue of concern." This is in the same spirit (few, targeted faults), but a language model generates the faults and the output is new tests, not a standing replay.

Searched for and NOT FOUND with this meaning: "regression mutants", "mutation-guided regression", "known-bug replay", "test the tests". "Regression Mutation Testing" (Zhang, Marinov, Zhang and Khurshid, ISSTA 2012) exists but means something else: reusing the results of automatically generated mutants from an older program version, which is the caching idea in section 3. The nearest everyday rule is that a regression test should fail before the fix and pass after it; [PARTIAL | Qt wiki, extract, wording approximate] that is checked once, when the fix is written. I found no source that re-checks it on every later commit (NOT FOUND). That repeated check is the unusual part of harness-kit, and it is a strength: it turns each past bug into a permanent guard.

**Why run time follows the number of faults, not the size of the code.** [VERIFIED for harness-kit from the `replay-faults.sh` header and `.harness/check-only`; the comparison is ASSUMPTION] With `.harness/check-only` present, each fault runs `<check command> --only '<check>'`, so only that check's test file runs. Cost per fault is therefore roughly one test file plus the setup of a throwaway copy, and the total is the number of faults times that, split over parallel machines. Adding lines of code does not add faults. Automatic tools do the opposite: they generate mutants in proportion to code size, which is why they need diff-scoping to stay fast.

## 2. What the tools' own documentation says about CI

**StrykerJS** (JavaScript and TypeScript; clone at commit f2a49ff, dated 2026-09-11, `docs/incremental.md` and `docs/configuration.md` read in full). [VERIFIED] Incremental mode: "StrykerJS will track the changes you make to your code and tests and only runs mutation testing on the changed code. But, of course, it will still provide you with the full mutation report at the end!" The reuse rule is that a mutant stays "Killed" if "the culprit test still exists, and it didn't change". The documented limit is: "Stryker will not detect any changes you've made in files other than mutated files and test files", and "any other changes to your environment are not detected, such as updates to other files, updated (dev) dependencies, changes to environment variables". Its `--force` option reruns everything. A `--since` option: NOT FOUND in StrykerJS (I searched its configuration document); it has `--mutate src/app.js:5-7` for line ranges. Its default `coverageAnalysis: perTest` runs only the tests that cover each mutant, and "does not influence the resulting mutation testing score". Its `thresholds.break` defaults to `null`, meaning the build never fails on the score. This is the second point that matters for you: **the documented risk of every narrowed run is the same, changes the tool cannot see**.

**Stryker.NET** (clone at commit 0a8e047, dated 2026-09-29). [VERIFIED] `--since` mutates only "code changes since the given target"; `--with-baseline` saves the report and reuses it, "which expands on the `since` feature by providing you with a full report after a partial mutation testrun". Its pipeline page says a "dashboard compare" cuts the total run time "by only testing mutations that have changed compared to for example master", and recommends `dotnet stryker --break-at 80` to fail the pipeline below a score.

**Pitest** (Java; clone at commit d7c2531, dated 2026-08-28, plus pitest.org extracts). [VERIFIED for the clone; PARTIAL for the site] Pitest first runs all tests with coverage probes and builds "a map that shows which lines of code are executed by each individual test", then runs only the covering tests per mutant. Mutant timeouts come from the measured baseline (factor 1.25 plus 4000 ms by default). Its own incremental analysis is called "experimental" and "currently unproven", with the warning that "class behaviour is defined not only by its bytecode, but also by its dependencies". **Changed-lines mode is not free any more:** the old free goal `scmMutationCoverage` was removed in Pitest 1.18.0 ("Fully remove deprecated scm maven goal", in the project's release notes), and the current route is the commercial Arcmutate git plugin, at $8 (Base) or $12 (Pro, includes the git integration) per user per month, free for open-source projects. [PARTIAL | price from an extract of arcmutate.com, fetched 2026-09-30] This does not affect you: harness-kit is bash and Node, and the gadget is JavaScript, where Stryker's free incremental mode applies.

**cargo-mutants** (Rust; clone at commit e838ca1, dated 2026-09-25; its whole book read in full). [VERIFIED] `--in-diff` "tests only mutants that overlap with regions changed in the diff", and the book adds this caution: "it's certainly possible that edits in one region cause code in a different region or a different file to no longer be well tested. Incremental tests are helpful for giving faster feedback, but they're not a substitute for a full test run." Also: "a diff that only deletes or changes test code won't cause any mutants to run, even though it may have a very material effect on test coverage." Its CI page names "at least two complementary ways": scoped to the pull request, and "checking that all mutants are caught, on PRs or on the development branch". Its sharding page gives the cost model `SHARD_STARTUP + (CLEAN_BUILD + TEST) + (N_TOTAL_MUTANTS / N_SHARDS) × (INCREMENTAL_BUILD + TEST)`, a rule of thumb of "at least 10 mutants" per worker, and 8 to 32 shards as a starting point. `--baseline=skip` exists so that "if you are sharding work in CI, this avoids running the baseline on each shard", provided "you must make sure that the tests are actually passing". That is the same design as harness-kit's `replay-baseline` job followed by `replay-shard` jobs. Its `--iterate` option, which skips mutants caught earlier, "is a heuristic" and "you should run again without `--iterate`" to be sure.

**Infection** (PHP; clone at commit 70148f4, dated 2026-09-30, plus extracts of its site). `--git-diff-lines` "mutates only added and changed files, comparing your current branch with `master` branch by default", and `--min-msi` / `--min-covered-msi` are "used with CI server to automatically control tests quality". [PARTIAL | extract] The documentation page on CI gave only threshold advice; the pull-request pattern is evidenced by the workflow files in section 5, not by prose (NOT FOUND in the docs I fetched).

**mutmut, Cosmic Ray, Mull, go-mutesting** (Python, Python, C and C++, Go; clones read). [VERIFIED for the clones] mutmut "remembers work that has been done" and runs only tests that could cover the mutant. Cosmic Ray's `cr-filter-git` skips "any mutation in a session that would mutate other lines" than the edited ones. Mull has `gitDiffRef: origin/main` for CI and claims reports "in the order of few seconds" with it (the tool's own claim; I did not measure it). go-mutesting has no diff option in its README (NOT FOUND) and warns that its accepted-mutation blacklist "is currently badly implemented", because a source change alters every checksum.

**A tool for shell scripts.** universalmutator (Alex Groce; clone last changed 2026-05-20) rewrites lines of code as text using regular-expression rules. [VERIFIED] It ships rule files for C, C++, Java, JavaScript, Python, Rust, Go and several others, and **none for bash**. It accepts your own rule file, so it could be driven by hand-written shell rules, but nothing ships ready. A maintained bash-specific mutation tool: **NOT FOUND**, searched three ways. That is why harness-kit's hand-written list is not a poor substitute for a standard tool: for bash there is no standard tool to use instead. [ASSUMPTION for the reading; VERIFIED for the search result]

## 3. What Google and Meta did about run time

**Google, "Practical Mutation Testing at Scale" (Petrović, Ivanković, Fraser and Just; arXiv 2102.11378, 22 February 2021).** [PARTIAL | extracts of the abstract and PDF; numbers as the tool reported them and not independently checked] Google mutates at code review and only changed lines: "Mutation testing is done incrementally, mutating only changed code during code review, rather than the entire code base." It generates at most one mutant per line, caps reported mutants at "7 times the number of total files in the changelist", skips "arid" code (for example a log statement, where a surviving mutant is not useful), and uses line coverage to "determine the minimal set of tests that need to be run in an attempt to kill a mutant". It reports 82% of surfaced mutants labelled productive by developers. The 2018 paper (ICSE-SEIP, extract) says re-computing the whole score after each commit "is almost imposible" (spelling as in the extract). Google's timeouts, full scheduled runs and sharding: NOT FOUND in the extracts, which does not prove they are absent from the full papers.

**Meta, ACH.** Run time and CI schedule: NOT FOUND. The paper is about generating tests; it says the generated tests were "submitted as diffs into the normal continuous integration review process".

**The techniques that keep run time bounded, each from a source above:**

1. Mutate only changed lines at review (Google, Infection, cargo-mutants, Mull, Stryker.NET, Cosmic Ray, Arcmutate).
2. Sample or cap: one mutant per line (Google), `--shard 1/100` for a one percent sample (cargo-mutants), one mutant per class (Arcmutate).
3. Run only the tests that cover each mutant (Google, Pitest, Stryker `perTest`, mutmut).
4. Reuse stored results (StrykerJS, Stryker.NET, Pitest history, Infection and phpstan result caches, mutmut, cargo-mutants `--iterate`), each with a documented "may miss indirect changes" warning.
5. Derive timeouts from a measured baseline (Pitest, Stryker, cargo-mutants).
6. Fail the build on a threshold (Stryker `break`, Infection `--min-msi`, Pitest `mutationThreshold`, Stryker.NET `--break-at`).
7. Shard across machines with one shared baseline (cargo-mutants).
8. Move the slow full run off the merge path, to nightly or weekly (Stryker.NET nightly, cargo-mutants weekly, stryker-js daily).

## 4. Answers to the four questions you asked

**(1) Is "scoped run on the branch plus a full run on a schedule" the mainstream shape?** [PARTIAL: yes in this sample] cargo-mutants recommends both in its own book. Infection runs a scoped job on pull requests and a full job on pushes to main. stryker-js runs an incremental job on pull requests, on the merge queue and daily, plus a plain run on pushes to master. PHP-CS-Fixer, phpstan-src and phpstan-doctrine run scoped only. Stryker.NET runs full only, nightly. In total, 7 of the 9 run a scoped or incremental job on each pull request, and 3 of the 9 run on a schedule. harness-kit's weekly full run is a normal ingredient. What harness-kit lacks is the **scoped run that gates the change before it merges**.

**(2) Is re-running a full run on `main` for a commit whose branch already passed it ever standard?** NOT FOUND as a stated practice in any document I read. cargo-mutants' example workflows (`basic.yml`, `sharded.yml`), its own CI and checkstyle's `pitest.yml` run the full run on both pull requests and pushes to main, and none of them discusses the duplication. With merge commits or squash merges, the commit on main differs from the branch head, so the second run tests something new. With your fast-forward merges the two are the same tree. [ASSUMPTION for the equivalence, reasoned from "fast-forward"] Two details make harness-kit's case different from what you may think. First, for a **normal change** the branch never ran the replay, so the run on `main` is the first one, not a duplicate. The duplicate exists only for a **machinery change**, which runs the full replay on the branch push and again on `main`. [VERIFIED | `validate.yml`] Second, Infection avoids the question entirely: its full workflow runs on pushes to main, and on pull requests only when the workflow file itself changes, because the pull-request check is the separate scoped job.

**(3) What is missing compared with mature practice?** In order of importance for "quality must not drop":

1. **A scoped run before merge.** Missing in CI for normal changes. [VERIFIED for harness-kit]
2. **A way to catch faults whose dependencies are missing from `check-files`.** The tools' own advice is a periodic full run, because a scoped run is "not a substitute for a full test run". [VERIFIED quote | cargo-mutants `in-diff.md`] You already have the weekly and machinery-triggered full runs, which is the right shape; see the counter-case below about the size of the gap.
3. **A view of how much of the code the faults cover.** Your rule is that all 137 faults must be killed, which is a 100% threshold on a fixed list. That is normal for a scoped run (Infection's diff job and both phpstan repositories use `--min-msi=100 --min-covered-msi=100`). For automatic full runs, real projects use lower thresholds (Infection 77 and 86 on itself; checkstyle 99 for some profiles) because unlisted survivors are expected. A curated list proves that the listed breaks are caught; it does not measure the strength of the tests elsewhere. [VERIFIED for the thresholds; ASSUMPTION that harness-kit has no such measure, since the replay reports only kills of listed faults]
4. **A trend of survivors.** Checkstyle commits 16 suppression files and a script that fails CI when a new survivor appears; Stryker keeps reports per branch on its dashboard. harness-kit keeps a REPLAYED line in a local events file and shows the age of the last CI replay at session start. A long-term record kept in the repository or as a CI artifact: NOT FOUND in the files I read. [PARTIAL: I did not read all of harness-kit]
5. **Result reuse keyed by content.** It exists in Stryker, Stryker.NET, Pitest, and in the phpstan repositories (an `actions/cache` entry keyed by run id with a prefix restore key), and every one of them documents a gap. For harness-kit a cache keyed by the hash of the fault, its target file, its test file and everything that test runs would be exactly as strong as the list of "everything that test runs" is complete. Bash tests can read files no list mentions. [ASSUMPTION] So caching is a later, riskier step than targeting, and it needs the same periodic full run as protection.
6. **Automatic mapping from fault to test.** Pitest and Stryker build it from a coverage run; harness-kit maintains it by hand. A tool that traces which files a bash test actually reads: NOT FOUND (not researched, no tool evaluated).

**(4) How does run time stay flat as the code base grows?** [VERIFIED per tool; the combination is ASSUMPTION] Automatic tools keep the merge path proportional to the change (scoping), run only covering tests per mutant, shard with the shard count scaled to the mutant count, and move the full run off the merge path. For harness-kit: a **full** replay grows linearly with the number of faults, because each new fault adds one more test-file run; a **targeted** replay depends only on how many faults are tied to the changed files, so it stays flat as the list grows provided changes stay small. The fixed cost of each machine (installing Node and Claude Code, checking out) does not grow with faults but is paid once per shard, 8 times in the current design. [VERIFIED for the structure | `validate.yml`; measured per-fault time after the recent optimisation: NOT FOUND]

## 6. Verdict on "full replay on every push to main, plus weekly"

1. **The frequency is inside the observed range and is not excessive in itself.** [PARTIAL] Five of nine sampled repositories run a full-scope run after a push, and Google's objection to re-running after each commit concerns generated mutants over billions of lines, not a fixed list of 137 faults that each run one test file. [ASSUMPTION for the last part]
2. **What is unusual is the detection point.** [VERIFIED for harness-kit; PARTIAL for the others] Gating projects find a surviving mutant on the pull request, in the changed scope, so their main does not turn red for a mutation reason. harness-kit's ordinary change gets no replay before merge, although the targeted replay exists. That matches your "late surprises".
3. **The duplicate on machinery branches is not standard but not condemned.** No source I read dedupes by tree, and no source describes the duplicate as intended.
4. **A weekly full run as the safety net for a scoped run is what cargo-mutants and Stryker.NET do.** [VERIFIED] If the per-branch run is targeted and a full run happens weekly, on machinery changes and at release, that is the mainstream shape. Running full on every `main` push as well is stronger than mainstream and costs more.
5. **For quality that must not drop, the safe reading is "add first, remove later".** Adding the targeted replay on branches strengthens detection at once. Removing the full run on `main` should wait until something equally strong stands in for it (a full replay just before release, on the exact commit that will land). File 06 sets that order.

## Strongest counter-cases

- **Against "scoped run on the branch plus weekly full is enough".** cargo-mutants itself warns that a scoped run is "not a substitute for a full test run", and its own CI runs both the scoped jobs and a 10-shard full run on every relevant push and pull request. harness-kit's selection rests on a hand-written map, which can be wrong silently. If quality must not drop at all, a full replay before merge for every change is the safest option. Its cost is the price of the current slowness, so the decision should follow a measurement of the full replay time (a step-0 item in file 06), not a guess.
- **Against "the run on main is waste".** With fast-forward merges the tree is identical, but the run is also an independent check on a clean machine with today's runner image and today's Claude Code installer, either of which can change between the branch run and the main run. [ASSUMPTION] The weekly run covers most of that, not all.
- **Against "a curated list needs no coverage view".** A curated list proves only the listed breaks are caught, and it can drift away from where the real risk is. Automatic mutation testing, or Google's developer feedback on which mutants matter, finds gaps nobody thought to list.
- **Against "post-merge full runs are unnecessary".** They exist in 5 of 9 sampled repositories, and in stryker-js the post-merge full run sits beside an incremental pull-request run because incremental reuse has documented blind spots. The PHP repositories without a post-merge run accept that untouched code is not rechecked, and they gate on a 100% score of changed lines only.
- **Against my sample.** Five of nine are mutation tools' own repositories, none is a shell project, and none uses a curated fault list. The counts (5 of 9, 7 of 9) describe these repositories and are not estimates of what mature users do in general.
- **Against the web quotations.** Most came through a summarising tool. Quotations from clones are exact. Google's and Meta's numbers are extract-level and should be re-read before they go into a decision record.
